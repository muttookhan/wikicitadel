# UUIDv7 identifier policy

Policy version 1.0.0, adopted 2026-10-22 (build wave 6, standards bundles pack). Standard: RFC 9562 section 5.7 (UUIDv7). Generated by scripts/wiki_standards_bundles.py from the policy table in that module — regenerate, never hand-edit.

## The default

Every NEW internal identifier minted by wiki tooling from adoption forward is a UUIDv7, unless the object's register already runs a grandfathered scheme (below), in which case the register's own scheme continues — one scheme per register, never two in one register.

Illustrative UUIDv7 (fixed all-zero parts, shown for shape only — not a minted id): `00000000-0000-7000-8000-000000000000`

## Minting rules

- time-ordered: the 48-bit unix millisecond field makes string order agree with mint order across milliseconds; identifiers sort by creation without a separate timestamp column
- no re-minting: an identifier, once written to any register or artefact, is never replaced; a correction appends a new record naming the old id, it does not rewrite the id
- legacy ids are never rewritten: grandfathered schemes keep issuing and resolving exactly as before; no migration, no alias table is created — each register remains the map for its own ids
- an id names the object, not its content: content identity stays with the house hashes (citation lockfile line hashes, checkpoint line hashes, merkle roots), which this policy does not touch
- mint through scripts/wiki_standards_bundles.py uuid7 new (or mint_uuid7 in this module) so the layout is the RFC's, verified against the RFC's own example vector in the test suite

## Grandfathered schemes (never rewritten)

- `cp-NNNNNN` — evaluation/checkpoints.jsonl: continues; checkpoint ids stay sequential and human-citable
- `ocr-NNNN` — evaluation/ocr-queue.jsonl: continues
- `pred-NNNN` — evaluation/predictions.jsonl: continues
- `fc-NNNN` — forecast ids cited across wiki pages: continues
- `weed-NNNN` — evaluation/weeding-nominations.jsonl: continues
- `UUIDv4 (runtime-minted)` — WARC record ids (scripts/wiki_warc.py, scripts/wiki_warc_capture.py): retained for WARC tooling interoperability; the ids are minted at capture time and stored in the WARC records themselves, not in a house register

## Out of scope

- content hashes (sha256 lock hashes, merkle roots, canonical export hashes) are identifiers OF content and are not replaced by UUIDs
- page paths and raw paths are the wiki's human identifiers and stay; the linked-data export's IRIs are derived from them, not from UUIDs
- external identifiers (DOIs, ORCIDs, git SHAs, message ids from other systems) are recorded as issued, never re-minted
- ephemeral protocol values minted at runtime (e.g. the multipart boundary in scripts/wiki_openrefine_trial.py) are not identifiers of record and are out of scope

## Gaps (stated, not smoothed)

- adoption is prospective and by convention: no existing tool is rewritten tonight to mint v7 — the first register that needs a new non-schemed identifier is where the default first applies, and that adoption is recorded when it happens
- within one millisecond, string order among v7 ids is random-tail order, not insertion order (RFC 9562 makes the same statement); a register that needs intra-millisecond order keeps its own sequence field
